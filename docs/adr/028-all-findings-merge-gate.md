# ADR-028 — All-Findings Merge Gate: Address Blocking and Non-Blocking Before Merge

**Date:** 2026-05-27
**Status:** Accepted
**Tags:** review, workflow, git, pr, blocking-rule, non-blocking
**Enforced by:** [ADR-039](039-merge-gate-findings-enforcement.md) — the `pre-merge-findings-gate` hook makes this policy a mechanical merge-time gate after it was violated by prose-only enforcement (PR #310).

---

## Context

The post-compact workflow rule in `claude/CLAUDE.md` previously read:

> "Address any **blocking** findings and merge in the same session."

In bypass permissions mode, Claude follows rules literally. "Any blocking findings" gave explicit
permission to skip non-blocking review findings — Claude would merge as soon as the blocking
bucket was empty, leaving non-blocking findings (performance, maintainability, documentation
suggestions) noted in the PR comment but never acted on.

Separately, the `/review` skill's Step 6 classified one sub-category of non-blocking finding —
the Step 2c suggestion to create a README where none exists — as "not required, but advisable."
This label created a two-tier system within non-blocking findings and would have directly
contradicted any stricter merge gate.

Two resolution options were considered:

**Option A (chosen):** Require all findings to be addressed before merging, with no "optional"
carve-outs. Remove the "not required" qualifier from the skill.

**Option B (rejected):** Require blocking findings to be addressed; require non-blocking findings
to be either addressed or explicitly deferred in the PR body with a justification note.

---

## Decision

**All findings** — blocking and non-blocking — must be addressed before `gh pr merge` is run.
No finding generated by `/review` is optional.

Two artifacts updated together (PRs #271–#272, amended in the same branch):

1. `claude/CLAUDE.md` line 78: "Address any blocking findings" → "Address **all** findings
   (blocking and non-blocking)."
2. `claude/skills/review/SKILL.md` Step 6: removed "(not required, but advisable)" from the
   Step 2c non-blocking bucket entry, so all non-blocking findings carry equal weight.

---

## Rationale

**Option B was rejected** because requiring deferral documentation for each non-blocking finding
adds friction proportional to the number of findings — a review with five minor suggestions
forces five explicit deferral notes. In practice this friction causes the notes to become
boilerplate ("deferred — out of scope") rather than genuine decisions, which is worse than
the original silent skipping.

**Option A enforces a clean invariant:** every finding in a review comment is closed before the
PR merges. The cost is occasional scope expansion when a review surfaces an easy non-blocking
fix (e.g., a missing README entry) — but that expansion is the desired behavior: the rule exists
precisely to prevent those fixes from accumulating silently.

This decision parallels ADR-022 (test coverage gate), which similarly made a previously-optional
declaration mandatory at merge time. The pattern is: if a review step generates an actionable
finding, merging without acting on it defeats the purpose of having the step.

---

## Consequences

- Non-blocking findings from `/review` are now merge-blocking in all autonomous sessions.
- The Step 2c "create a README" suggestion — previously labeled optional — is now required if
  surfaced by a review. Authors who genuinely believe the suggestion is wrong should remove the
  finding from the review comment or resolve the ambiguity via the "Questions for Author" bucket
  before the merge step runs.
- If a non-blocking finding is genuinely out of scope for the current PR (e.g., it concerns
  unrelated code), the correct action is to open a follow-up issue, address the finding by
  linking to that issue in the PR body, and then merge. The finding is "addressed" once it has
  a tracked home — it does not have to be fixed in the same PR.

## Addendum (2026-06-05) — "Fix everything, always" behavioral default

ADR-028 establishes *what* must happen (every finding closed before merge) and the two valid
dispositions (fixed-in-PR or filed-and-linked). It did not specify the *default behavior* an
agent should take when it reaches the findings list. In lifting-logbook PR #452 the agent
emitted a correct review (0 blocking, 2 non-blocking, 1 design question), then paused to ask the
user *which* findings to fix and offered a fix-vs-defer menu. The user's response — **"Fix
everything, always"** — establishes the missing default:

1. **Do not ask which findings to fix.** Resolve all of them as part of the same work. A
   choose-which-to-fix menu or a "should I proceed?" prompt is the wrong default — it adds a
   round-trip and risks findings being silently dropped.
2. **Prefer fixing in-PR over filing.** Filing-and-linking remains valid (see Consequences
   above) but only for findings genuinely out of scope for the current PR. The default is the
   in-PR fix.
3. **Prefer the root-cause fix over the band-aid**, even when the band-aid is smaller. In #452
   the symptom was a duplicate `environment: production` declaration; the root cause was a
   separate `approve-production` job built on the false premise that two jobs sharing one
   environment prompt only once (GitHub prompts per-job). The chosen fix deleted the job and
   consolidated the gate onto the deploy job, which simultaneously closed both non-blocking
   findings and the design question — a band-aid (patch the stale doc, accept the misattributed
   deployment record) would have left the underlying defect in place.

**Escalation exceptions** (the only cases where asking the user is correct): a fix requires a
product/design decision the code cannot settle, or it would breach the scope guard in
`claude/CLAUDE.md` → *Code Quality → Fix errors on encounter* (>~75% scope increase).

[dev-env#319](https://github.com/brownm09/dev-env/issues/319). It complies with the Durable
